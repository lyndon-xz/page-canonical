# 取数与编排

## 请求发出前先把上一轮结果作废

两个页面的 `loadXxx` 都要先作废「派生于这一份结果集」的所有状态。具体清哪些各页不同，取决于该页有哪些这类状态：

- homestay：列表、选中房源、整组详情上下文、待确认的操作
- hotel：列表、总条数、已加载页码、hasMore、上一轮的翻页失败态、选中酒店、多选集合、批量失败清单、已提交的预订

原因是 store 是页面级单例、不随页面卸载重置。少了这段，loading 期间的条数报的是上一次的数字，选中态与详情也会指向已经不在结果里的条目。

**归零之后，UI 不能把归零值当结论。** `hotelsTotal` 清成 0，而「找到 N 家」直接读它，于是转圈期间用户读到的是「找到 0 家」——一个比旧数字更糟的答案：旧数字至少是过期的真话，0 是一句凭空的假话。所以这行文案先看取数状态，加载中显示「搜索中…」。判据可以推广：清空是为了不让过期值蒙人，不是为了让占位值冒充结果，凡是直接渲染被清字段的地方都要先问一句「现在是不是正在取」。

收藏（`favoriteIds`）两页都不清——那是跨结果集的用户数据，不属于「这一份结果」。

**这段清理收在状态层的一个 reducer 里**（两页都叫 `resetResultSet`），不在 action 里连着 dispatch 好几句。散着写有两处代价：中间态会真实存在，读者与订阅者都可能看到「列表已空但选中态还指着旧房源」；更要紧的是新增一个派生于结果集的状态时，没有任何东西提醒你回来补一句，而漏掉的那个字段要等用户换一次筛选条件才暴露。

同一条理由也适用于比它小的整组归零。homestay 的「退出当前房源」牵涉选中态与三个详情字段，因此有 `exitListing`；`resetResultSet` 复用它，两者的关系是包含而非并列。少清其中任何一个都会留下痕迹：漏了 `isDetailDrawerOpen`，抽屉随模块卸载看似关闭而开关仍是 `true`，下次点开任意房源就自动弹出；漏了 `detailStatus`，下一套房会先闪一帧上一套的失败占位。

## 请求竞态用自增序号守卫

快速切换选中项时，先发的请求可能后到，直接写入会让详情与当前选中的项不符。

做法是每次请求领取一个自增序号，只有最新序号的响应允许落库：

```ts
const requestId = (latestRequestId += 1);
const isCurrent = () => requestId === latestRequestId;
```

几个要点：

**序号放模块变量，不放 store。** 它只服务请求编排，UI 从不读它。进 store 会白白多一次渲染。

**用自增序号而不是「参数去重」。** 去重会让重复选中同一项无法重新拉取，漏掉重试场景。

**过期请求连状态都不该动。** catch 分支里也要先判 `isCurrent()` 再写 error，否则会把仍在飞的那次请求的 loading 提前收掉。

**「谁是最新请求」和「结果还有人要吗」是两个条件。** 清空结果的动作也得让未返回的请求失效，否则它会把数据写回刚清空的 store。两种解法：

- homestay 的详情在守卫里加一条校验：序号最新**且** `selectedListingId` 未变。适合清空动作有多个来源的情况（这里除了换筛选条件，listener 也会清）。
- hotel 的列表反过来在清空处推进序号（`resultSetGeneration`）。适合清空只有一个来源的情况，不必引入额外校验。它的序号是「结果集的代号」而非单次请求的编号：换筛选条件即另起一代，翻页只读不递增、延续当前一代，因此首页与翻页共用同一个。

## 分页与无限滚动

**`hasMore` 由服务端明确给出**，不靠 `items.length < pageSize` 推断。末页刚好满页时那种推断会多请求一次空页，还会让「加载更多」多闪一下。

**总数与已加载条数是两个值。** `hotelsTotal` 是匹配筛选条件的总条数，用于「找到 N 家」；`hotels.length` 随分页累加。每页都跟服务端重新对齐 total，因为期间别人可能增删了酒店。

**排序是取数参数，不是展示态。** 列表分页加载，排序必须由服务端在全量数据上做。放前端排已加载的部分，会让新到的一页插进已展示的卡片之间、整列重排。所以换排序等于换一次取数条件，要回到第一页重新拉。

**用 IntersectionObserver 而非 scroll 事件。** 后者要自己算容器高度与阈值、还得节流，换个滚动容器就失效。

**并发守卫只放一处。** 哨兵会连续触发，「没有下一页 / 已有请求未返回 / 首屏还没回来」这三个判断统一在 `loadMoreHotels` 里，effects 只负责观察视口。缺了守卫就会并发拉同一页、把重复数据追加进列表。

**换筛选条件时要把上一轮的翻页失败态清掉。** 否则新列表仍显示「下一页加载失败」框，而哨兵因失败态不渲染，无限滚动就此失效。

**加载更多的状态与首屏分开。** 首屏 loading 要盖住整个列表，加载更多只在列表末尾转圈。加载更多失败时保留 `hasMore`——失败不代表没有下一页，用户可以原地重试。

**换条件后视口只在必要时回到列表顶部。** 用户在页底换筛选或排序时，列表缩回一页而视口还停在下方，末尾哨兵可能立刻又进视口、多拉一页。所以换条件后要把视口带回列表顶部——但这件事有三个约束，缺一个都会让它自己变成 bug。

**判断当前位置，别无条件滚。** 「视口停在列表下方」是前提，不是每次换条件都成立。用户在页面顶部点排序时列表顶部本就在视口内，此时还滚一次，等于把他从刚点的那个控件旁边推走：hero 与整个筛选卡片被顶出视口上方。所以先量一次位置，只有列表顶部已经滚出视口上方才回滚：

```ts
if (!list || list.getBoundingClientRect().top >= 0) {
  return;
}

list.scrollIntoView({ behavior: "auto", block: "start" });
```

**滚动归 effects，不归 action。** 写在 `applySearchParams` 里会量错布局：`loadHotels` 同步跑完 `resetResultSet` 与 `setHotelsStatus(Loading)` 就交出控制权，而 React 是批处理的，此时 DOM 还是旧的长列表。`scrollIntoView` 量的是这份即将被丢弃的布局，滚过去；紧接着列表塌成一个 spinner、页面高度骤降，浏览器把 `scrollTop` 夹回可滚动上限，落点于是不可预测。放进 effect（依赖 `appliedParams`）才能保证量的是重置后的真实布局，顺带也省掉了 live 表里那个只为滚动存在的 DOM ref。

**滚动用 `behavior: "auto"` 而非 `"smooth"`。** 平滑滚动要几百毫秒，取数比它先回来，哨兵会在视口还没归位时重新挂载并立刻触发下一页。

**滚动目标要给吸顶栏留位。** `block: "start"` 把列表顶部对齐到视口顶部，而 layout 的导航栏是 `position: sticky; top: 0`，于是列表标题、全选框与排序条正好被它盖住。补偿写在列表自己的样式表里（`scroll-margin-top: 84px`），不必让 JS 去量导航栏高度。

**哨兵是条件渲染的，观察器要跟着它的存在性重挂。** 首屏 loading 时哨兵不在 DOM 里，`ref.current` 为 `null`。effect 只依赖 ref 的话只跑一次，且那一次什么都没观察到，之后哨兵出现也不会补挂——所以要把「哨兵该不该渲染」作为显式依赖传进 effect。这个条件由四个状态字段推导，归 model（`showSentinel`），渲染分支与观察器都从那里取同一个值，落地写法见[分支渲染](branching.md)。

**mock 数据的条数要多于一页。** 首屏若填不满一屏，哨兵一开始就落在视口里，会自动连锁翻页直到取完，反而看不出滚动加载的效果。

**每条错误分支都要有可触发的 mock 条件。** 收藏与预订各有一个被拒的 id、一个被拒的手机号，而 `fetchHotelPage` 一度永不失败——`FetchStatus.Error` 那段占位与重试按钮于是没人能走到，也就没人能发现它写错了没有。触发条件要可控，别用「随机失败」或「第一次必失败」：搜 `error` 这个关键词才失败，不影响正常浏览，需要演示时又随时能进去。

翻页失败（`loadMoreStatus === Error`）目前仍走不到：18 条数据、每页 12 条，只有一次翻页，而任何让第 2 页失败的条件都会连第 1 页一起挡掉。要补就得先把 mock 数据加到三页以上，那时再让某一页失败才不影响前面的成功路径。

## 乐观更新的适用范围

**单项收藏用乐观更新。** 高频轻操作，等 300ms 再亮起会让人觉得点了没反应。先按预期改本地，再发请求，失败回滚。

回滚用请求前的快照，而不是「再取反一次」——并发点击下取反会把状态推到错的一边。回滚之后还要给 toast：星标弹回去只表示「没生效」，用户还需要知道为什么。

**批量收藏刻意不用乐观更新。** 单项失败只需回滚一个值，批量的结果是「部分成功」：先全亮起再挑几个回滚，中间态会让用户以为全成了。所以等结果回来再落库，成功项并入收藏，失败项点名给用户并保留在选中态里供原地重试。

**批量的落库不能拿请求前的快照做覆盖。** 它的写入在 `await` 之后，期间用户完全可以单项收藏别的酒店。用请求前读到的 `favoriteIds` 与成功项合并，就会把那一次单项收藏抹掉。所以落库时重新读一次当前值再求并集——与下面 homestay 那条是同一个道理，判据都是「写入是否发生在 `await` 之后」。

**属于结果集的那部分写入要过代号守卫。** 成功项并入收藏可以照写，收藏是跨结果集的用户数据；但失败清单与「保留勾选供重试」属于当前这一份结果集。批量收藏在飞、用户换了筛选条件时，这两句会把上一份结果集的 id 写进新结果集：批量操作条显示「已选 N 家」而没有一张卡片是勾选的，`batchFailureNames` 也因为在新列表里找不到那些 id 而把文案退化成裸 id。所以它们写入前要判一次 `isCurrentGeneration`，catch 分支同理。

**homestay 的收藏是悲观更新**（先等接口成功再改状态），与 hotel 形成对照：它的取消收藏要走二次确认，弹窗本身已经提供了「正在处理」的反馈，抢先改状态没有收益。

悲观更新要自己补上进行中的反馈。乐观更新的心标是立刻亮的，反馈天然存在；悲观更新那一路上心标要等接口回来才变，什么都不做的话用户点下去只能看着它不动，于是重复点。所以 homestay 存一份 `favoritingIds`，按房源给按钮 loading 与禁用，`toggleFavorite` 也据此挡掉进行中的重复点击。

**悲观更新的落库要走增删，不能用请求前的快照做覆盖。** 状态写在 `await` 之后，两次收藏的请求会重叠：各自读到的都是自己发请求时的 `favoriteIds`，谁后返回谁的快照胜出，先落库的那一条被抹掉。所以 homestay 的收藏在 slice 里是 `addFavoriteId` / `removeFavoriteId` 两个增删 reducer，action 只决定「本次是收还是取消」。

hotel 的**单项**收藏不必如此，是因为乐观更新把状态写在了 `await` 之前，第二次点击读到的已经是新值——它的快照只用于失败回滚。顺序一改就不再安全，上面批量收藏那条正是同一个坑的另一头。

## 批量操作的接口形状

批量接口整批一次请求，逐项返回成败（HTTP 200 + body 里带逐项结果），而不是有一项失败就返回 4xx。后者让调用方无法区分「全失败」和「部分失败」，整体抛错还会连带丢掉已经成功的那部分，用户重试时重复提交。

只有整个请求没发出去时才全部按失败处理——此时逐项成败无从得知。

## 错误处理的分工

**取数 action 自己 catch，翻成 `FetchStatus.Error`。** 结果态已在请求前清空，catch 里只翻状态。

**提交 action 不接错误，只用 finally 保证 loading 收尾。** 字段级错误要回填到表单，得由调用方拿到原错误分流。模块 action 接住它：homestay 的 `InquirySubmitError` 与 hotel 的 `BookingSubmitError` 里的字段错误逐个 `setError` 到对应输入框，其余走 toast。字段级错误不再弹 toast——同一件事说两遍。

**写入的唯一出口向上抛，由调用方决定怎么反馈。** homestay 的 `commitFavorite` 有两条调用路径：确认弹窗要把错误留在弹窗内，直接收藏走 toast。所以它自己不处理错误。

**不吞掉 rejection。** 没人接的 rejection 等于失败静默。
